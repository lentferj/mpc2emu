# Closing the `–` cells in `PARAMETER_MATRIX.md` — implementation plans

**Audience: a person or an AI who did not write any of this.** Each entry says
what the cell is, where the code lives, what is already known, **what has to be
decided or measured before code is written**, the steps, and how to prove it
worked. Symbols are cited rather than line numbers, because line numbers rot.

`docs/PARAMETER_MATRIX.md` is generated by `tools/parameter_matrix.py` and
classifies every dash already. This file is the *how*. The two must agree:
`tests/test_parameter_matrix.py` fails if a dash has no recorded reason, and if
a reason survives the cell ceasing to be a dash.

---

## Read this before starting any item

This project has a specific failure history, and these rules exist because each
one cost something. They are not ceremony.

1. **Score against an oracle, not against intuition.** Device-written banks we
   hold: `~/temp/B030-AKAIIMPORT-full.E4B` (E4XT's AKAI import),
   `~/temp/EPSTEST.e4b`, `~/temp/ROLTEST.e4b`, `~/temp/K2K_EPS.krz`,
   `~/temp/rlndcd2/*.KRZ`, `~/temp/K2K_AKAI.krz`.
2. **Compute the base rate before believing a correlation.** Two hypotheses
   died on 2026-09-25 that each explained 78 % of their target set — against a
   base rate of 72 %. Ask: *what fraction of the cells my rule does NOT target
   does it also cover?*
3. **A round trip tests symmetry, not correctness.** Reader and writer can be
   wrong in the same way and agree perfectly — that is exactly how the KRZ LFO
   shape sat at byte 4 on both sides for months. Only an external referent (a
   device bank, the panel, the corpus distribution) separates them.
4. **Never invent a rail fraction.** A bare `depth * 50` assumes the panel
   rail *is* the law. It is not: the real laws carry a measured coefficient on
   top of it — `AKAI_LFO_PAN_DEPTH_SCALE` makes the write `depth * 50 * 0.1563`,
   and the KRZ panner's is 0.4377 for the same-looking quantity. If you need a
   scale, either reuse one measured for **the same rail** and say so, or measure
   it. Two constants that look interchangeable usually are not.
5. **Run the whole suite and read its exit code.** `pytest … | tail && git
   commit` reports *tail's* status. That has put a red commit in this history
   twice.
6. **State inferred vs measured.** A caveat that outlives its measurement makes
   correct code look wrong; a missing one makes a guess look measured.

Verification harnesses that already exist and should be reused rather than
rewritten: `tests/test_parameter_matrix.py`, `tests/test_krz_lfo2.py`,
`tests/test_akai_pan_matrix_law.py`, `tests/test_eos_foreign_sim_vs_device.py`.

## A. `lfo_volume_centre_db` → AKAI

The KRZ half of this item is **DONE** (2026-09-25) — see *Closed* at the end.
What is left is the AKAI half, and it is a different job: not arithmetic, a
missing measurement.

<details><summary>A1 — KRZ, for reference (closed)</summary>

**What it is.** The DC level a tremolo swings *about*. The model carries it
because the MPC states it; without it a tremolo is centred on the wrong level
and the whole voice sits too loud or too quiet.

**Why it is a dash.** `krz_writer` already writes the AMP `Adjust` byte —
`KRZ_F4_AMP_ADJUST_INDEX` (= 1) in `seg(0x53)`, at
`KRZ_F4_AMP_ADJUST_DB_PER_UNIT` (= 1.0 dB/unit) — but it writes only the
*tremolo headroom trim*. Two quantities want one byte.

**The decision to make first.** They are both in dB and both offsets to the same
level, so they **add**; that is already how `level_offset_db` combines the
headroom trim with the velocity-pivot offset in the same function. Confirm that
reading before coding — the relevant comment is at the "TWO THINGS MOVE THIS
BYTE" block in `_patch_layer`.

**Steps.**
1. In `writers/krz_writer.py`, in `_patch_layer`, add
   `getattr(voice, 'lfo_volume_centre_db', 0.0)` into the existing
   `level_offset_db` accumulation rather than writing `Adjust` separately.
2. Keep the single clamped write — the comment there explains why two writes
   and two clamps were wrong.

**Verify.** `lfo_volume_centre_db` non-zero must move `seg(0x53)[1]` by
`round(centre_db / 1.0)` relative to the same voice with it zero, and a voice
with no tremolo and no centre must be byte-identical to today's output.

**Trap.** The clamp is `±KRZ_F4_AMP_DEPTH_CLAMP`. Adding a second contributor
makes saturation reachable where it was not; assert the clamp rather than
assuming headroom.

### AKAI: blocked on one measurement

**Recorded reason:** *"no measured centre-offset rail on this machine."* The
machine can hold a static level — `docs/AKAI_S3000_FORMAT.md` documents a
program-level **stereo level, offset `0x17`, 0–99, 99 = full** — but **how many
dB one unit of it is worth has never been measured here.** Without that number
a centre offset in dB cannot be turned into a byte.

**⚠ The obvious shortcut is the known mistake.**
`AKAI_LFO_LOUDNESS_DB_PER_PRODUCT` (0.010068) is *right there* and is in dB, but
it calibrates the **tremolo mod-matrix product** (`LFODEP × amount`), which is a
different rail from a static output level. Reusing it would be exactly the
"invented rail fraction" failure that rule 4 above exists for — and it would look
measured, because the constant is.

**Measurement (one sweep, the existing rig).**
1. One program, one keygroup, one steady tone, everything else neutral. Vary
   only `0x17` across its range — e.g. 99, 70, 50, 30, 15, 5.
2. Capture through `tests/re_banks/hw_measure.py` at the **pre-EQ tap**, and
   include an unmodulated negative control.
3. Fit dB against the byte. Do not assume linear-in-dB: the tremolo law turned
   out to be a *product* law, established by equal-product equivalence rather
   than by linearity in either variable. Test the shape before naming the
   constant.
4. Record it in `models/common.py` beside the other AKAI rails, with the
   method and date in its docstring, and add the §-section to
   `docs/RESOLUTION_NOTES.md`.

**Then** the write is the same shape as A1 — fold the centre into whatever
already sets the level byte, one clamped write.

**Also check, while the rig is out:** whether the byte is program-level only.
If it is, a bank whose voices want *different* centres cannot express them, and
that is a `content_lost` diagnostic rather than a silent average.

## F. `key_to_pan` → KRZ — *needs the slope's PIVOT measured, then a span decision*

**What exists.** The panner's `KeyTrk` is hardware-mapped: program offset 244,
seg index 3 (offset − 241), **0.2 %/key per unit, ±16 %/key** (§PANMOD).
`writers/krz_writer.py` already declares `_K2_PAN_ADJUST, _K2_PAN_SRC1,
_K2_PAN_DEPTH = 1, 5, 6` and `_K2_PAN_VELTRK = 4`; `KeyTrk` would be 3.

**Why it is not a transcription.** `KeyTrk` is a **slope** (pan per key). Our
`key_to_pan` is a **scalar depth**. Converting one to the other needs an
assumed keyboard span: "full depth over how many keys?"

**⚠ AND A SECOND BLOCKER THIS PLAN ORIGINALLY MISSED: the PIVOT.**
`KeyTrk` is a slope, and a slope needs the key it rotates about. That key is
**not recorded anywhere** — not in `docs/KRZ_FORMAT.md`, which gives the offset
and the rail and no pivot, and not in `krz_parser`, which never reads the field.
§KRZRESKEYTRK asks the same question for `F2 RES KeyTrk` and lists it as
unknown, with `resonance(key) = Adjust + KeyTrk * (key - 60)` written down
explicitly as a *hypothesis*.

For resonance a wrong pivot is a tilt. For **pan** it is much worse: guess C4
when the machine pivots at C1 and the whole voice arrives panned hard to one
side. So this item needs **one hardware measurement** — set `KeyTrk`, play three
widely spaced keys, find the one that does not move — and it is not a
no-hardware item however the span question is settled.

**Steps, once the pivot is known.**
1. Decide the span and write the reasoning down. Candidates: the voice's own
   key range (`lo_key..hi_key`), a fixed 128, or the source's own centre.
2. Only then pick the byte value.

**Do NOT** reuse `KRZ_LFO_PAN_DEPTH_SCALE` here. That constant calibrates the
**2 %/unit** depth rail; `KeyTrk` is a **0.2 %/key** rail. They are different
quantities that happen to live in the same block — the `VelTrk` case (A above,
already implemented) was legitimate precisely *because* it shares `Depth`'s
encoding, and this one does not.

**Verify.** With a decided span, a source whose pan spreads across the keyboard
must produce a `KeyTrk` whose implied total swing matches. This is arithmetic,
then an audible check.

**LFO2 is not the same job.** LFO1's law is a product with `LFODEP`; LFO2's own

uncalibrated rail — rule 4.

**The tempting shortcut is the known-bad one.** Routing an LFO2 tremolo onto

routings confound.

Once the constant exists the write is a copy of LFO1's, using
`AKAI_MOD_SOURCE_LFO2` (8) in a free `MODSAMP` slot.

## H. `lfo1_to_filter_cents`, `lfo2_to_filter_cents` → AKAI — *the model half is DONE; a rail is behind it*

**The model blocker was real and is now fixed** (2026-09-25). This plan said
the field had "no single defined full scale", and that was true three ways
over: `cents/10800` to `krz_parser`, `cents/4383` to the SF2 and SFZ readers,
and a raw EOS cord amount to `e4b_parser` — so one 4383-cent sweep arrived as
0.406 from a K2000 and 1.000 from an SFZ.

The plan's own suggested fix — pick one constant — **would not have worked**,
and proving that is what settled the design. What a full E4XT filter cord is
worth in cents depends on where the corner already sits: 4383 cents costs cord
amount 66.2 at `vpar[60]` = 60 and 14.0 at 220, nearly 5×, and it saturates. No
constant exists to divide by. The field therefore carries **cents**, renamed
`*_to_filter_cents`, following `filter_env_cents` and
`velocity_to_filter_cents`. Every reader already had cents in hand.

**What is left is a measurement, and this plan cited the wrong constant for
it.** It claimed "the rail is measured at ~216 cents/unit (§AKAIF2DEPTH)".
(That figure is itself superseded — §AKAIF2DEPTH now reads **~230 +/-8** (s3ked §227), and 216.6 was OUR baseline window. The wrong-QUANTITY error described here is unaffected: filter 2 is still a different block from filter 1.)
That constant is `MODVFLT2_3` — the **filter 2** matrix, a different block.
For filter 1:

* only `MODVFILT1` has been measured at all, and its law is **velocity
  specific**: `cents = 4.368 × MODVFILT1 × (velocity − 64.56)`. It carries a
  velocity pivot and says nothing about an LFO source.
* `docs/AKAI_S3000_FORMAT.md` records every other `MODV*` range as *"still
  transcribed"*.
* LFO routings on this machine go through a program-level depth, so the law is
  very likely a **product** like the tremolo's — which means it has to be
  established by equal-product equivalence, not by sweeping one variable.

**So this is a bench item, not a code item.** One sweep covers both cells and
should also take LFO2's point, whose depth is `PANDEP` rather than `LFODEP`.

### ✅ THE SWEEP HAPPENED, 2026-09-26 (s3ked §270) — and the prediction above held

`cents peak-to-peak = ~4.0 × LFODEP × MODVFILT1`, measured on hardware with
`MODSFILT1 = 7` (LFO1), `FILFRQ` 70, `LFORAT` 8.

**It is a product, and it was established the way the bullet above said it had
to be** — by equal-product equivalence, not by sweeping one variable. Product
held at 400 while the split varied 6.25× each way:

    LFODEP × amount   20×20   40×10   10×40   50×8   8×50
    excursion (cents)  1565    1629    1634   1547   1549

Spread 5.3 % of the mean; an independent amount sweep agrees to 1 %. The
evidence is recorded here rather than only the section number, deliberately —
a section id is a dependency, a described measurement is a copy that survives
its source being withdrawn.

⚠ **Fitted over products 40-400 ONLY.** At 700 and 1000 the corner sweeps to
2593 and 3463 Hz, past the 2500 Hz band edge, so those points are excluded and
**compression above product 400 is unmeasured** rather than absent.

**What is left is now a DESIGN decision, not a measurement**, which is why this
cell does not simply close: `LFODEP` is program-wide and also drives the pitch
LFO, so a cents target has **no unique `(LFODEP, MODVFILT1)` split**. Choosing
one rescales the vibrato; choosing the other rescales every filter destination
sharing the amount. This is the same non-invertible collapse already recorded
for tremolo, and it wants the same answer, decided once for both.

**LFO2's point is still not taken** — its depth is `PANDEP`, not `LFODEP`, so
nothing here transfers to it.

### The split has a determinate answer (s3ked, `f66f60c`) — and it implies a ceiling

**The two factors are not symmetric, which is what dissolves the "no unique
split" objection above:**

    LFODEP     program 34     0..99    PROGRAM-WIDE, shared by every LFO1 target
    MODVFILT1  keygroup 151  -50..50   per keygroup, per slot, filter only

`LFODEP` is a **shared bus** and the amounts are **per-destination taps**. So it
is not a two-way split repeated per destination; it is one free parameter with
N constraints:

    amount_i = target_i / (k_i * LFODEP),  |amount_i| <= 50
    =>  LFODEP >= max_i( target_i / (50 * k_i) )

**And the objective is forced rather than chosen, because quantisation runs the
other way.** The amount is an integer, so the reachable step on destination *i*
is `k_i * LFODEP`. For filter 1 at `k = 4.0`:

    LFODEP   1:  step   4.0 ct,  max    200 ct
    LFODEP  20:  step  80.0 ct,  max   4000 ct
    LFODEP  99:  step 396.0 ct,  max  19800 ct

So the **smallest feasible `LFODEP` is simultaneously the finest-resolution one
on every destination at once** — a unique optimum, not a tie broken by
convention. Solve across the whole routed set, not per destination. One rule
answers tremolo and filter together, which is what this plan wanted.

⚠ **AND IT IMPLIES A CEILING ON DYNAMIC RANGE. Two of us stated that ceiling
wrongly before it was right, each by quoting it outside its regime.**

Writing `d_i = target_i / k_i` (demand in amount-units at `LFODEP` 1),
feasibility forces `L = ceil(max_i d_i / 50)`, and destination *j* rounds to
**zero** when `d_j < L/2`. The achievable range across destinations is
therefore

    range  =  2 * max(d) / ceil( max(d) / 50 )

**mpc2emu first said a flat 100:1.** That is the continuous bound and it is
reached only when `max(d)` is an exact multiple of 50; `ceil` can only make the
threshold worse.

**s3ked corrected it to 50:1..100:1** — right, and the correction matters,
because one unit above a multiple it collapses:

    max(d)    L   range        max(d)    L   range
        50    1   100.0 : 1       101    3    67.3 : 1
        51    2    51.0 : 1       150    3   100.0 : 1
       100    2   100.0 : 1       201    5    80.4 : 1

⚠ **But that table starts at `max(d)` = 50, and below it there is a worse
regime neither of us looked at.** For `max(d) < 50` the ceiling `L` is already
1 and cannot go lower, so the zero-threshold sticks at 0.5 and

    range  =  2 * max(d)        (max(d) <= 50)

    max(d)    1     5    10    25    49
    range   2:1  10:1  20:1  50:1  98:1

**A patch whose largest demand is small has almost no usable dynamic range at
all** — at `max(d)` = 10 a second destination is lost below one twentieth of
the first. **So "50:1" is as wrong as "100:1" was, in the same way: a bound
quoted outside the regime it was derived in.** The formula is the statement;
the ratios are summaries of it.

What survives every version of this, and is the part worth keeping: the bound
is **independent of the coefficients**, needing only `|amount| <= 50` and
integer steps. It therefore applies to pan and to the unmeasured slots whatever
their `k` turns out to be. Arithmetic, not measurement.

**The practical form is a detectable precondition, not a limitation to
document:** a writer computes `max(d)/d_j` before emitting anything and refuses
or reports, rather than emitting a tap that rounds to zero. Same defect class
as the AKAI zero-guard already covered by a regression test here, where a later
zero silently clobbered an earlier routing.

**What is missing is coefficients, not structure.** `k` is measured for filter 1
(s3ked §270), loudness (§173) and pitch (§160). **Pan has no law at all** —
§265 showed `PANDEP` gates it but never measured the shape. And
`MODVFILT2/3` / `MODVAMP2/3` are unmeasured: **whether they share slot 1's
coefficient is an assumption nobody has tested**, and a writer must not make it
silently.

⚠ **`LFODEP` is itself modulated** by `MWLDEP`/`PRSDEP`/`VELDEP` (program
36/37/38), so the shared bus moves at play time and rescales every destination
together. Any writer treating it as static is describing the **resting state
only**.

**And that undercuts the optimum further than "resting state only" suggests**
(s3ked's point back). If those rescale `LFODEP` during performance then the
smallest-feasible-`L` solve is optimal for one instant, and a patch played with
the modwheel up is running a different `L` — **with a different zero-threshold,
so destinations can drop in and out as the wheel moves.**

**[?] Whether that is real depends on something nobody has established: does
the machine apply `MWLDEP`/`PRSDEP`/`VELDEP` BEFORE or AFTER the amount
multiply?** Before, and the effect above is real. After, and the tap ratios
hold and only the overall depth moves. One sweep of §270's shape with `MWLDEP`
non-zero would decide it — worth taking only if this cell ever justifies a
writer.

## I. `lfo1_to_filter_q`, `lfo2_to_filter_q` → KRZ, AKAI — *KRZ slot located; both need the law*

Resonance modulation.

**KRZ — the slot is no longer unknown** (corpus, 2026-09-25). This plan called
the F2 block's modulation inputs "a hypothesis by analogy" with F1. The corpus
promotes it to evidence: over **16 649 layers**, `seg(0x51)[5]` is non-zero on
18.6 %, **never exceeds 127** (consistent with a source enum, inconsistent with
a free depth byte), and `[6]` accompanies it 86.9 % of the time — which is how
a Src/Depth pair behaves, since a source with no depth does nothing. **LFO1
(114) appears 37 times and LFO2 (116) 119 times**, so real material routes LFOs
to resonance on this machine.

**What is missing is the DEPTH LAW**, and that is not a free choice:
§KRZRESKEYTRK is Jan's standing decision that `F2 RES` must be measured before
it is written, taken after this project was caught three times by a plausible
reading of a displayed unit. One SysEx panel diff answers it (`read_object_bytes`,
panel edit with the editor open, read again, diff — RAM only).

**AKAI — no slot identified**, and no resonance-modulation entry exists in

## K. `mod_routings` → KRZ — *needs a units bridge*

**The AKAI half is DONE** (2026-09-25) — see *Closed*. It was implementable
precisely because nothing had to be fitted: the model carries the E4 cord
amount that EOS's own importer computes from those keygroup bytes, so writing
them back is that rescaler run backwards.

**The K2000 half is not the same job.** It has the destinations — ENVCTL
carries `Att Source`, `Att KeyTrk`, `Dec KeyTrk` and `Rel KeyTrk`, and this
writer already drives `Att VelTrk` on a measured span. What it does not have is
a bridge: the model's amount is in **EOS cord units**, and no measured law
relates one of those to a K2000 `VelTrk` or `KeyTrk` unit. Writing one would be
a guessed scale on an unmeasured rail — rule 4.

Note the prevalence before spending anything on it (§AKAICORDGAP): the seven
routings run 3.1 %, 1.0 %, 0.4 %, 0.4 % of keygroups and three are near zero.

**Two ways to close it**, neither requiring the AKAI: measure the K2000's
`Rel KeyTrk`/`VelTrk` in seconds-per-unit by SysEx panel diff, which gives a
physical unit both sides can meet in; or carry the routing amount as a physical
quantity in the model the way `velocity_to_amp_attack_span` already does for
the one routing we convert properly.

# How to prove any of these actually worked

1. **Unit** — a focused test beside the existing ones, and **mutate it**: break
   the thing it guards and watch it fail. A guard never made to fail is
   indistinguishable from a comment.
2. **Round trip** — write, read back, compare. Necessary, never sufficient
   (rule 3).
3. **External referent** — score against a device oracle, or the corpus
   distribution, or the panel. This is the step that catches symmetric errors.
4. **Regenerate** `docs/PARAMETER_MATRIX.md`; the dash must be gone and its
   entry in `DASH_REASONS` must go with it — `test_parameter_matrix.py` fails
   otherwise, deliberately.
5. **Whole suite, exit code read directly.** Then `tools/relscan.py` before any
   commit that touches tracked files.

# Closed — what was implemented on 2026-09-25, and how

Kept here rather than deleted, because each one settled a question the open
items still ask, and because a reader who finds a similar cell should be able to
see the shape of a finished answer.

### `lfo_volume_centre_db` → KRZ
Folded into the AMP `Adjust` accumulation in `krz_writer._patch_layer`. Three
quantities now share that byte — the tremolo headroom trim, the velocity-pivot
offset and the source's tremolo centre — and they **add**, because all three are
static dB offsets to one level at 1.0 dB/unit. The `±96` rail is now reachable
where two contributors could not reach it, so saturation is **reported** rather
than absorbed: the E4XT resolves the same squeeze by keeping the centre and
letting the swing give way (`e4xt_tremolo_cords`, Jan 2026-09-17), and doing
that here would mean rewriting `Depth` below its measured request. That is a
decision for Jan, so the swing is kept and the shortfall is logged.

### `velocity_to_filter_min_cents` → E4B
The floor moves `vpar[60]` and the cord carries the **span**, `max - min`. This
works only because the velocity→cutoff cord is `Vel+` (0x0A), where vel 0 = base
cutoff; under the EOS template's own `Vel<` the arithmetic would be wrong at
both ends, so the test asserts that source id rather than assuming it. It has to
happen before the byte is written, since every cord amount is converted against
it (§FENVFULLSCALE). The wide-open `255` override is now gated on there being no
floor. **This closed a collapse, not an omission:** `(0, +10800)` and
`(-5400, +5400)` used to produce identical bytes, and they are different
patches.

⚠ **The obvious test for this proved nothing and was caught by mutating it.**
"Raise the floor, watch the cord amount shrink" passes while the writer still
carries the depth, because raising the floor also raises the base byte and
cents-per-cord grows with the corner. Only `min == max` — a sweep that does not
move, so the amount must be **zero** — separates the span from the base shift.

### `lfo1_to_volume` → AKAI
`MODSAMP3` (0x58) repointed to source 7, amount solved into the keygroup-level
`MODVAMP3` (155). Three things worth carrying forward:

* **Slot 3 because its amount is per KEYGROUP.** Slots 1 and 2 take
  program-level amounts, so on either of them a bank whose keygroups want
  different tremolos would have to share one number.
* **The free-`LFODEP` trick.** The law is a product and `LFODEP` is the vibrato
  depth, so a tremolo is inexpressible at `LFODEP 0` — where 206 of 213 real
  programs sit. But `L_PTCH` gates LFO1→pitch separately and is written 0 when
  no vibrato is stated, so `LFODEP` is then free; taking it to 99 also pins the
  mod wheel out of the tremolo. See `AKAI_LFO1_DEPTH_FOR_TREMOLO_ONLY`.
* **`_PROGRAM_HW_DEFAULTS` runs LAST.** 0x58 is one of its entries, so writing
  the slot earlier is silently undone — leaving a program whose amount is solved
  against depth 99 while the slot still names Velocity. The note beside that loop
  documents exactly this for `PANRAT`; the first version of this change walked
  into it anyway, and a test asserting the source byte caught it.

### `transpose` → KRZ and AKAI
Folded into the same semitone term as `coarse_tune` on both. The model keeps
the two apart because the E4XT has a byte for each — `vpar[34]` remaps the
keyboard, `vpar[35]` repitches the sample — but neither other machine has that
distinction: the K2000's keymap `Xpose` shifts pitch by exactly what it
transposes (measured, and it ADDS to the pitch page's `Coarse`), and the AKAI
has no identified key-remap parameter at all.

⚠ **This plan told the next reader the field was unidentified and to grep
`docs/KRZ_FORMAT.md` first. Doing that is what found it** — offset 178, keymap
`Xpose`, hardware-read by k2kremote §73, and `krz_parser` has read it since
2026-09-14. Writing "not identified" without having run the grep is the exact
failure the instruction was warning about.

⚠ **The first probe of this was inconclusive and looked conclusive.**
`krz_parser` folds transposition into `root_key`/`fine_tune` and writes
`transpose` back as 0, so watching the `transpose` field showed zero whether the
writer worked or not. A `coarse_tune` control through the same path — the one
field known to survive — is what made the drop visible, and every test carries
one.

⚠ **And the ceiling half nearly shipped untested.** Transposing up spends the
K2000's 48 kHz up-pitch headroom, so the term belongs in the ceiling
computation too — but removing it there left every pitch test green, because the
clip is not observable through `parse_krz` at all (contiguous keymap ranges).
The writer's own over-ceiling diagnostic is observable, and that is what the
test uses. The same path had no coverage for `coarse_tune` either.

### `program_number` → KRZ
A program's object id **is** its program number on this machine (`bank = id //
100`, `PC = id % 100`), so honouring the source's number is a matter of choosing
ids rather than writing a field. Safe because a program's own id is referenced
by nothing — programs point at keymaps, nothing points at a program.

Two limits are reported rather than absorbed: user objects start at **200**, so
a source asking for program 130 cannot have it (the old code put it on 200 and
said nothing); and two presets cannot share a number, which is the AKAI writer's
PRGNUM hazard — four programs on one number all sound at once on one program
change. Requests win in preset order, the loser is told, and unstated presets
fill the gaps.

### `lfo*_to_filter` → cents, and `mod_routings` → AKAI
The filter field became `lfo1_to_filter_cents` / `lfo2_to_filter_cents` across
five readers and three writers. The rename is deliberate: a silent unit change
on an unchanged name is how a "correct number, wrong quantity" error gets made,
and this file has now produced two of those in one day.

`mod_routings` → AKAI writes the seven §AKAICORDGAP routings back to their
keygroup bytes by inverting EOS's rescaler. Four depths cannot survive — the
101 values ±50 map onto 97 cord bytes, so (12, 13), (37, 38) and their
negatives collide — and that is asserted across the whole rail rather than
worked around, so nobody later "fixes" it by inventing a scale.

⚠ **Two tests in this work proved nothing until they were mutated.** The
span test for the E4B filter floor passed while the writer still carried the
depth; and the zero-guard test here passed with the guard deleted, because a
keygroup buffer is zero-filled and writing 0 is indistinguishable from not
writing. The guard only bites when a later zero would overwrite an earlier
routing, which is what the corrected test does.

### `velocity_to_pan` → E4B, as `Vel~`
Censused, not decided. Across three EOS-native library CD-ROMs: **2 127 cords
into `AmpPan`, every one `Vel~`**, zero `Vel+`, zero `Vel<` — against 96.9 %
`Vel+` for `AmpVol` on the largest of the same discs. Two destinations on one
machine with opposite conventions.

⚠ **The control leg is the load-bearing part.** Run against `AmpVol` the same
scan reproduces §E4XTVELSRC's recorded table to the unit (11 banks / 11 806
voices / 11 449 / 36 / 238), so the mechanism is validated rather than trusted.
The first pass had no such validation and would have chosen the wrong form: it
scanned 131 loose `.e4b` files, found 8 cords, all `Vel+` — and that
population's own volume control comes back 100 % `Vel<` against the CDs' 96.9 %
`Vel+`, marking it as converted third-party material, the same kind of wrong
subject as the 22 resident presets that produced the original refuted claim.

`e4b_parser` had to be written too: it read **neither** pan cord the writer
emits, so `velocity_to_pan` and `key_to_pan` both vanished on an E4B → E4B
conversion.

⚠ Two claims of mine were wrong along the way and are recorded rather than
quietly dropped: that the ISO population was unreachable without writing an
extractor (`tests/re_banks/extract_emu_hdd_bank.py` reads those images
directly, and had for weeks), and — in item H — that the AKAI filter rail was
measured at ~216 cents/unit, which is the *filter 2* matrix's constant.

### `chorus_amount` → KRZ
The K2000 carries no chorus depth in a program — the `0x0F` segment *selects*
an effect object by id, and we reference ROM effects rather than authoring
type-28 objects. So the amount is expressed the only way the machine allows
without a new object type: select ROM preset **31, `Stereo Chorus`** — the only
one of the factory 47 that is chorus with no reverb or delay bolted on — and
set its Wet/Dry from the amount.

Two costs, both stated in the code rather than discovered later. It **replaces**
the program's effect (the template's `Sweet Hall`), because the machine has one
global effect per program and something must lose; and the chorus's own rate and
depth are the ROM preset's, so two sources differing in chorus character differ
here only in level.

⚠ **Byte 2 is inferred to be Wet/Dry Adjust, not measured.** The program EFFECT
page holds exactly one 0..100 parameter against six that are −128..127; and
across **4 280 corpus programs byte 2 never exceeds 86** — never >100, never
>127 — where a signed Depth would be expected to produce both. That is an
exhaustive negative, not a measurement, and a SysEx panel diff would settle it.

### `non_transpose` → AKAI
Four flags, **one per velocity zone** — `CP1..CP4` at keygroup bytes 132–135,
`0 = TRACK, 1 = CONST` (s3ked, from the SysEx spec's wording; document-derived,
not hardware-confirmed).

⚠ **Not the single per-keygroup switch this plan assumed.** Setting only `CP1`
gives a keygroup that plays at constant pitch when struck softly and tracks the
keyboard when struck hard — which presents as an intermittent fault rather than
as a wrong byte. All four are written, including unused zones, so a later edit
that adds a zone inherits the behaviour the source asked for.

⚠ **And "constant pitch" is not "at its own root".** CONST sounds the sample at
a constant KEY (the manual says C3); our field means the sample plays at ITS
root. They coincide only where the root already is that key. `KGTUNO`/`VTUNO`
stay live on top so it is correctable in tuning — but the octave convention
behind `AKAI_CONST_PITCH_KEY` is itself assumed, so the writer **reports the
exact semitone offset** rather than compensating on an assumed constant.

That diagnostic silently did not fire when first written: it read `root_key`
off the built zone entries rather than the model's zones, so every root came
back `None`. Found by probing a case that should have warned and seeing
nothing — the guard, not the feature, was the broken half.

### `non_transpose` → KRZ
`CAL[19]`, the PITCH page's KeyTrk, written as byte **213** — signed −43,
displaying −100 ct/key, which meets the KEYMAP page's default +100 exactly.
Measured on hardware 2026-09-26 (k2kremote set the byte, mpc2emu captured;
full record, fit points and all three refuted candidates in §KRZPITCHKEYTRK):
PITCH 0 gives **+97.9 ct/key over 48 keys**, PITCH 213 gives **+0.0** — 201.43 Hz
at every one of five keys, spread 0 cents against the control's 4712.

That also answered a standing question in the affirmative direction for once:
**§90's three-region ladder describes the ENGINE, not just the display.** On this
machine that could not be assumed — the policy exists because a displayed unit
has been wrong three times.

⚠ **THREE VALUES LOOKED RIGHT FIRST AND ALL THREE WERE WRONG.** `0` is a no-op
(98.78 % of 16 649 layers carry it). `43` is the opposite, +100 ct/key, double
tracking. And "the engine uses the raw byte −43 as cents-per-key" fitted a
**single key** to 12 cents — an artefact, because the test leg is flat and the
control tracks, so their difference at one key is just the control's tracking
evaluated there. Five keys separate those models by 2 736 cents. A linear fit of
that difference gave "slope −97.9, pivot 66.6", which is the control's own slope
sign-flipped and the crossing of two lines: neither number about the field at
all.

**The multi-zone route deliberately.** `CAL[3] = 0` also gives zero total
tracking but stretches one sample root across the keyboard. Real material does
it that way — 950 programs, drums enriched 9.7× — against a population of **one**
for this byte, so ours is measured rather than idiomatic, and the test asserts
that `CAL[3]` is left alone.
